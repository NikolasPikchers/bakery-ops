# Страница «Ассортимент» — дизайн

Дата: 2026-11-18 · Точка: Плюшкино (point-1, единственная с iiko)

## Зачем

Владелец хочет **сократить линейку**: понять, от каких позиций можно отказаться почти без потери выручки.
Это не «рейтинг продаж ради рейтинга», а инструмент решения: список кандидатов на вывод и ответ на вопрос
«уберу эти позиции — сколько потеряю».

Сейчас сервис хранит из iiko только итог дня (`Revenue`: выручка и доля кондитерки). Разбивка по блюдам
приходит в том же OLAP-запросе и выбрасывается.

## Что известно из данных (разведка 18.11.2026, iiko OLAP SALES)

- История по блюдам есть с **2026-01-03** (313 учётных дней, ~22 тыс. строк «день × блюдо»).
- `DishId` устойчив: у каждого id одно имя (iiko отдаёт текущее), переименование не рвёт историю —
  **группировать по `DishId`**, имя брать последнее.
- Чековый разрез (`UniqOrderId.Id × DishId`) работает: 30 дней = 8,8 тыс. строк, ~4 тыс. чеков, 2 с.
- Себестоимость (`ProductCostBase.ProductCost`) заполнена только у ~половины блюд (у всей кондитерки и,
  например, «Пиццы куриной» — 0). Наценку можно показывать только там, где она есть.
- Группы iiko: «Сытная мелкоштучка», «Сладкая мелкоштучка», «Кофе, чай, напитки, фри», «ЛПЗ»,
  «Заказные пироги», «ТЕСТО»; у кондитерки (`\`) группы нет. Префиксы имён: `//` — сытное, `\` — кондитерка.
- За 3 месяца (18.08–17.11): 127 позиций с продажами; из них 6 служебных (пакеты, стаканчики, сиропы),
  8 заказных пирогов, 26 уже не продаются (сезонное: лимонад до 02.11, медовик шоколадный и т. п.),
  3 новинки («Курочка по-корейски» — с 04.10). Оцениваем 87: A = 41 позиция (77% выручки),
  B = 25 (15%), C = 21 (5%).
- Ловушки, которые страница должна обходить: новинка выглядит аутсайдером («Курочка по-корейски»: 9 шт.
  за 30 дней, но в продаже 6 недель); сезонное выглядит мёртвым; позиция, которую пекут не каждый день,
  выглядит слабой по выручке, хотя в дни продажи её разбирают (трайфлы: 9 дней из 92, 2,6 шт./день).

## Цели / не цели / анти-цели

- **Цель:** видеть кандидатов на сокращение и цену их вывода; решение принимает владелец.
- **Не цель (пока):** план выпечки по дням недели, остатки и списания (бумажные листы не ведутся),
  вторая точка, рекомендации «убрать автоматически».
- **Анти-цель:** список, который советует убрать новинку, сезонную позицию или то, что просто редко пекут, —
  владелец перестанет ему верить.

## Подходы (выбран 2)

1. **Разовый отчёт** — выгрузить историю, прислать таблицу. Быстро, но одноразово; не видно эффекта
   после сокращения.
2. **Страница в сервисе (выбрано владельцем).** Продажи по блюдам сохраняются каждую ночь, история
   с января; кандидаты и «что потеряю» всегда под рукой, после сокращения видно, перешли ли покупатели
   на другое.
3. ~~Запрашивать iiko на лету при открытии страницы~~ — без новой таблицы, но медленно (окна по 31 дню,
   несколько запросов на сравнение периодов) и страница не работает, когда iiko лежит. Отброшен.

## Данные

Новая таблица (Prisma):

```prisma
model DishSale {
  id         String   @id @default(cuid())
  pointId    String
  point      Point    @relation(fields: [pointId], references: [id])
  date       DateTime @db.Date   // учётный день iiko
  dishId     String              // iiko DishId — ключ позиции
  name       String              // имя из iiko на момент загрузки
  dishGroup  String?             // группа iiko (у кондитерки нет)
  qty        Decimal  @db.Decimal(12, 3)
  revenue    Decimal  @db.Decimal(12, 2) // DishDiscountSumInt — как в Revenue
  cost       Decimal  @db.Decimal(12, 2) // 0 = себестоимость в iiko не заполнена
  checks     Int                  // чеков с этой позицией
  soloChecks Int                  // чеков, где кроме неё только служебное (пакет и т. п.)
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt

  @@unique([pointId, date, dishId])
  @@index([pointId, date])
}
```

Загрузка — `IikoClient.getDishSales(from, till)`: один OLAP-запрос на отрезок ≤ 31 дня с разрезом
`OpenDate.Typed × UniqOrderId.Id × DishId × DishName × DishGroup`, агрегаты `DishAmountInt`,
`DishDiscountSumInt`, `ProductCostBase.ProductCost`; свёртка по чекам до «день × блюдо» — чистая функция
с тестами. Запись — заменой дня целиком (удалить строки дня → вставить), в транзакции: блюдо может
исчезнуть из дня, если заказ удалили задним числом.

Когда:
- **Ночью** вместе с выручкой (`runIikoSync`, окно «вчера + сегодня»). Падение загрузки блюд не должно
  ломать выручку и наоборот — отдельные шаги, обе ошибки видны в логе.
- **Кнопка «Обновить из iiko»** на дашборде (`/api/revenue/iiko-sync`) — тоже подтягивает блюда.
- **История** — `/api/cron/iiko-sync?from&till` (CRON_SECRET; сейчас роут без периода — добавить
  период, режется по 31 дню) и CLI `npm run import:iiko -- --from --till`. Разовая загрузка
  с 2026-01-01 запускается на проде (база Timeweb с Mac не всегда доступна).

## Классификация позиций (чистое ядро `src/lib/assortment/`)

**Категория** (для фильтра): префикс `//` → «Сытное»; `\` → «Кондитерка»; иначе по группе iiko:
«Сытная мелкоштучка» → «Сытное», «Сладкая мелкоштучка» → «Сладкая выпечка»,
«Кофе, чай, напитки, фри» и «ЛПЗ» → «Напитки», «Заказные пироги» → «Под заказ»; остальное → «Прочее»
(бургеры, хлеб, тесто). Префикс важнее группы — так же считает `isConfectionery`.

**Служебное**: имя совпадает с `пакет|стаканчик|упаковка|доп\.|сироп|соус` — в таблице скрыто,
в выручку периода для долей не входит.

**Статус** позиции относительно периода (по умолчанию — 3 месяца по вчерашний день):
- **Новинка** — первая продажа в истории позже, чем за 60 дней до конца периода. Не кандидат.
- **Не продаётся** — нет продаж последние 14 дней. Отдельный свёрнутый список с датой последней продажи
  («сезонное или уже снято»). Не кандидат.
- **Под заказ** — категория «Под заказ». В таблице есть, не кандидат.
- **Оцениваемая** — всё остальное.

**ABC** среди оцениваемых по выручке за период: A — набирают первые 80%, B — следующие 15%, C — последние 5%.
**Кандидаты на сокращение = класс C.** ABC всегда считается по всей линейке; фильтр категории только
скрывает строки (иначе «C внутри напитков» не говорит, сколько теряет пекарня).

**В продаже** (KPI) — не служебные позиции с продажами за последние 14 дней. Доли («% выручки») везде —
от выручки периода без служебного.

## Метрики по позиции (за период)

- Выручка и ₽ в месяц (выручка / дней периода × 30); доля от выручки периода.
- Штук всего; **дней в продаже** из дней работы точки; **штук в день продажи** — отделяет «не берут»
  от «редко пекут».
- **Тренд**: последние 30 дней к предыдущим 30, % (без значения, если в одном из окон 0); мини-график
  по неделям за период.
- **Берут отдельно**: soloChecks / checks, % — показываем при ≥ 20 чеках, иначе «мало данных».
  Высокий процент = ради неё приходят, вывод рискованнее.
- **Наценка**, % — только если себестоимость заполнена во всех днях периода с продажами, иначе «—».
- В продаже с (первая продажа в истории).

## Страница `/assortment` (только владелец)

Вкладка «Ассортимент» в меню после «Разбивки». Шапка: «Ассортимент · Плюшкино», переключатель периода
**1 / 3 / 6 / 12 мес.** (по умолчанию 3), фильтр-чипы категорий. Оформление — существующие `_ui.tsx`
и `_charts.tsx`, как «Разбивка» и «Расходы».

```
Ассортимент · Плюшкино                         [1 мес · 3 мес · 6 мес · 12 мес]
[Все] [Сытное] [Сладкая выпечка] [Кондитерка] [Напитки] [Под заказ] [Прочее]

 В продаже 90   A 41 · 77%   B 25 · 15%   C 21 · 5%   Новинки 3

 Кандидаты на сокращение (класс C) ▾
 ☐ C  Ириска с гим. солью   1 490 ₽/мес  0,1%  34 из 92 дн  1,9 шт/день  ▼12%  ▁▂▁▁  отдельно —
 ☐ C  Капуста с мясом       3 540 ₽/мес  0,2%  23 из 92 дн  5,2 шт/день  ▲8%   ▁▃▂▃  отдельно 9%
 …
 Все позиции ▾  (сортировка по выручке ↑/↓, по клику на колонку)
 ☐ A  Пицца классическая  103 600 ₽/мес  6,0% …
 Новинки ▸ · Не продаются (последняя продажа) ▸

 ┌ Отмечено 5 позиций: 14 200 ₽/мес — 0,8% выручки · отдельно их брали в 6% чеков ┐
```

Отмечать можно любые позиции (не только C). Плашка «что потеряю» — оценка сверху: часть покупателей
возьмёт другое. Отметки не сохраняются (решение владельца живёт у него в голове/таблице) — при желании
позже.

Имя в таблице — без префикса `//` / `\` (категория и так видна), остальное как в iiko.

**Карточка на главном дашборде**: «Ассортимент: в продаже N · кандидатов на сокращение M (X% выручки) →».

## Оставлено исполнителю

- Агрегация в SQL (`group by dishId` и по неделям) или в коде — по объёму: 12 месяцев ≈ 25 тыс. строк.
- Миграция — как у прошлых таблиц; доступ — уже закрыт для сотрудников (`accessDecision` пускает
  их только в `/staff`), новых правил не нужно.
- Валидация периода в cron-роуте — по образцу `parseSyncRange` из Т-Бизнеса (до 366 дней).

## Проверка готовности

- Сумма `DishSale.revenue` за день = `Revenue.amount` того же дня (iiko) — сверка на истории.
- Тесты ядра на реальных кейсах из разведки: новинка («Курочка по-корейски»), сезонное («Лимонад»),
  редко пекут (трайфл), служебное (пакет), категория по префиксу важнее группы («\ Пончики на сметане»).
- После загрузки истории на проде — страница за 3 месяца даёт ~21 кандидата, ~5% выручки.

## Решения, принятые без владельца (можно поменять)

- Порог C = последние 5% выручки; новинка — младше 60 дней; «не продаётся» — 14 дней без продаж.
- Период по умолчанию 3 месяца; варианты 1/3/6/12.
- Отметки «что потеряю» не сохраняются.
- Карточка на главном дашборде — краткая, со ссылкой.
- Служебные позиции определяются по имени (список слов выше).
