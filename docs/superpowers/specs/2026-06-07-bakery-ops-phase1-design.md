**Дата:** 2026-06-07

**Автор:** Nikas (с Claude)

## 1. Контекст и проблема

Пекарня с **двумя точками**. Касса — **iiko**, денежные расходы идут через **Т-Бизнес**.
Отдельная и главная боль: **ежедневный учёт движения товара ведётся вручную на бумаге** — на печатных
шаблонах и от руки. Эти листы никто не сводит, данные не оцифрованы, реальные остатки нигде не видны
в цифре.

«Приход-расход», который изначально упоминался, по факту оказался **движением товара в штуках**
(не деньгами): сколько испекли/завезли, сколько осталось, сколько списали — по каждой позиции, по датам,
по точке.

Это спека **только Фазы 1**. Деньги (Т-Бизнес), выручка/продажи с кассы (iiko) и полная экономика —
отдельные фазы (см. §13).

### Что на листах (по реальным фото)

Два формата:

1. **Печатный шаблон-таблица.** Слева напечатан фиксированный список товаров; сверху — даты; под каждой
   датой подколонки **Приход / Остаток / Списание**. Руками вписаны количества. Один лист охватывает
   несколько дней (в образцах — 2–6 колонок дат). Так ведут пироги/выпечку и десерты
   (на листе десертов цены уже напечатаны).
2. **Свободная рукопись.** Просто «товар — число+число = итог», блоками (напр. «Остатки», «Бенто»).
   Так иногда ведут кондитерку.

Распределение по точкам:
- **Точка 1:** пироги/выпечка + десерты.
- **Точка 2:** только десерты.

### Семантика записи в ячейках (зафиксировано)

- **Приход «a+b+c»** — несколько партий (допеки/довозы) за день; итог = сумма. Пример: `24+12+6` → 42.
- **Остаток «x−y»** — остаток с поправкой/списанием прямо в клетке; разрешаем в одно число. Пример: `13−1` → 12.
- **Кружок ⑨** (в рукописи) — итоговое значение остатка.
- **Остаток переходит на следующий день** (carryover).
- Базовая формула продаж:
  **Продано(день) = Остаток(пред. день) + Приход(день) − Списание(день) − Остаток(день).**
  Проверено на образце (Самса: 3 + 8 − 0 − 9 = 2) — сходится.

## 2. Цели Фазы 1

1. **Оцифровать листы** обоих форматов в единый структурированный реестр движения товара.
2. **Реальные остатки** по каждой позиции, точке и дате — главный результат (приоритетное поле).
3. **Захват «и там, и там»:** Telegram-бот (фото с точки) + загрузка/правки на сайте.
4. **Подтверждение с правками:** распознанное всегда проходит ревью человеком; столбец «Остаток» и
   ячейки с низкой уверенностью подсвечиваются.
5. **Свод и дашборд:** остатки сейчас, продажи и списания по товарам/дням/точкам.
6. **Заложить aging для Точки 2** в модель данных (включается, как только накопятся остатки за несколько
   дней) — подсветка позиций, лежащих **> N дней** (по умолчанию 5, настраивается на товар).

### Не-цели Фазы 1 (out of scope)

- Интеграция с iiko (выручка/продажи с кассы) — Фаза 3.
- Интеграция с Т-Бизнес (денежные расходы) — Фаза 2.
- Перевод штук в деньги (₽), прайс, P&L — Фазы 2–3 (модель данных оставляет задел: опц. поле цены).
- Управление рецептурами/себестоимостью/закупками — Фаза 4+.
- Мультипользовательские роли/права сверх «владелец + доверенные» (см. §11).

## 3. Глоссарий

- **SKU / позиция** — товар из каталога (напр. «Самса», «Пицца открытая», «Бенто Орео»).
- **Точка** — торговая точка (Точка 1 / Точка 2).
- **Тип листа** — `pies` (пироги/выпечка), `desserts` (десерты), `confectionery_freeform` (рукопись кондитерки).
- **Лист (sheet)** — один загруженный снимок/скан + его метаданные и распознанное содержимое.
- **Движение (movement)** — факт по одной позиции за одну дату на одной точке: приход/остаток/списание.
- **Возраст остатка** — дней с последнего прихода по позиции, пока остаток > 0 (метрика aging).

## 4. Архитектура (Стек A)

Единое приложение **Next.js (App Router) на Vercel**:

- **Веб-дашборд + API** — Next.js.
- **БД** — Postgres (Neon через Vercel; Prisma как ORM).
- **Хранилище изображений** — Vercel Blob (оригиналы фото листов).
- **Telegram-бот** — webhook-эндпойнт в Next.js (Vercel Function); allowlist chat_id.
- **Распознавание** — Anthropic API (vision): основной `claude-sonnet-4-6`, эскалация на
  `claude-opus-4-8` для низкой уверенности и для свободной рукописи. Structured output через tool-use
  (строгая JSON-схема).
- **Auth** — NextAuth (как в других проектах Nikas), вход для владельца + доверенных.
- **Деплой** — Vercel (привычный паттерн: salary-radar / marketplace-reviews).

Почему A: несколько точек + захват из любого места → нужен облачный доступ; один репозиторий проще
поддерживать; ровно привычный стек. Ключи (Anthropic, Telegram, БД) — в env Vercel.

Принцип изоляции: распознавание (vision) вынесено за чёткий интерфейс
`recognizeSheet(image, catalog, sheetType) → RecognitionResult` и не знает ничего про БД/UI; его можно
тестировать и менять (другая модель/движок) независимо.

## 5. Модель данных

Postgres (Prisma). Ключевые таблицы:

### `points`
- `id`, `name` (Точка 1 / Точка 2), `created_at`.

### `products` (мастер-каталог SKU)
- `id`, `name`, `sheet_type` (`pies` | `desserts` | `confectionery_freeform`),
- `point_scope` — на каких точках встречается (обе / только Т1 / только Т2),
- `shelf_life_days` (nullable) — порог aging для позиции (для десертов Точки 2),
- `default_price` (nullable, decimal) — задел под деньги (Фазы 2–3),
- `aliases` (text[]) — варианты написания/сокращения с листов (напр. «Пирожок (беккен) с капустой»),
- `active` (bool), `created_at`.

Каталог фиксированный (печатный шаблон) → ведётся в админке; распознавание мапит строки на него.

### `sheets` (загруженный снимок)
- `id`, `point_id`, `sheet_type`,
- `image_url` (Vercel Blob), `image_hash` (для дедупа),
- `dates` (date[]) — какие даты-колонки распознаны на листе,
- `source` (`telegram` | `web`), `uploaded_by`,
- `status` (`uploaded` | `recognized` | `needs_review` | `confirmed`),
- `raw_recognition` (jsonb) — полный ответ модели,
- `created_at`, `confirmed_at`.

### `movements` (факт-таблица — ядро)
- `id`, `point_id`, `product_id`, `date`,
- `prihod` (int, nullable) — итог по партиям,
- `ostatok` (int, nullable) — **приоритетное поле**, разрешённое в одно число,
- `spisanie` (int, nullable),
- `sold_calc` (int, nullable) — вычисленное продано (см. §8); хранится денормализованно для скорости,
- `sheet_id` (fk), `confidence` (float 0..1 по строке), `raw_cell` (jsonb: исходный текст ячеек),
- `manually_edited` (bool), `created_at`, `updated_at`.
- Уникальность: `(point_id, product_id, date)` — повторная загрузка обновляет, не дублирует.

### `unknown_lines` (нераспознанные/новые позиции)
- `id`, `sheet_id`, `point_id`, `date`, `raw_text`, `parsed_numbers` (jsonb),
- `status` (`pending` | `mapped` | `ignored`), `mapped_product_id` (nullable).
- Для строк, которых нет в каталоге (дописанные от руки) — выносятся на решение человека.

## 6. Распознавание (vision)

**Ключевой рычаг точности:** список товаров напечатан и фиксирован. Модель не читает «с нуля», а
заполняет количества по **известному каталогу** для конкретной (точка, тип).

### Вход
- Изображение листа (после предобработки: автоповорот/выравнивание/контраст).
- Мастер-каталог SKU (имена + aliases) для `(point, sheet_type)`.
- Тип листа (`pies` / `desserts` / `confectionery_freeform`).

### Промпт-стратегия
- Для **печатных шаблонов:** «вот список ожидаемых строк по порядку; вот колонки дат с подколонками
  Приход/Остаток/Списание; верни для каждой найденной строки числа по каждой дате, парся выражения
  `a+b+c` (сумма) и `x−y` (вычитание), кружок = итог; если строка пустая — null; если встретил строку
  не из списка — верни её в `unknown_lines`».
- Для **свободной рукописи:** «извлеки пары `позиция — выражение — итог`, посчитай итог; помечай низкую
  уверенность». Сразу эскалация на `claude-opus-4-8`.

### Выход (строгая JSON-схема, tool-use)
```
RecognitionResult {
  point_hint, sheet_type, dates: [ISO date, ...],
  rows: [ {
    product_name_raw, matched_product_id|null, match_confidence,
    cells: [ { date, prihod, ostatok, spisanie, raw_cell, cell_confidence } ]
  } ],
  unknown_lines: [ { raw_text, parsed_numbers, cell_confidence } ],
  warnings: [string]
}
```

### Уверенность и правки
- Каждая ячейка несёт `cell_confidence`; **весь столбец «Остаток» и всё, что ниже порога, обязательно
  подсвечивается** на подтверждении.
- **`raw_cell` (исходный текст) сохраняется всегда** — ничего не теряется, правки быстрые.

### Ожидания по точности (честно)
- Печатные шаблоны (структура известна) — высокая надёжность; основное — выверка чисел в «Остаток».
- Свободная рукопись (кондитерка Точки 2) — заметно ниже; больше ручных правок. Это отдельный режим,
  не блокирует остальное.

## 7. Поток обработки

1. **Захват.**
   - *Telegram:* пользователь шлёт фото листа → бот спрашивает/угадывает точку и тип → кладёт в Blob,
     создаёт `sheet (status=uploaded)`.
   - *Веб:* загрузка фото на сайте с выбором точки/типа.
2. **Распознавание.** Серверный вызов `recognizeSheet(...)` → `sheet.raw_recognition`,
   предварительные `movements` (status переводится в `recognized`/`needs_review`).
3. **Подтверждение.**
   - *Telegram:* бот присылает сводку распознанного (с подсветкой неуверенных ячеек и «Остаток»),
     быстрые правки или «всё ок».
   - *Веб:* таблица-редактор с подсветкой; правки сохраняются в `movements (manually_edited=true)`.
   - `unknown_lines` — отдельный блок «новые позиции»: смапить на каталог / добавить SKU / игнор.
4. **Фиксация.** `sheet.status=confirmed`; пересчёт производных (`sold_calc`, остатки, aging).

## 8. Свод и вычисления

Всё выводится из `movements`:

- **Текущий остаток** по позиции/точке = `ostatok` последней даты с заполненным остатком.
- **Продано(день)** = `ostatok(пред. дата)` + `prihod(день)` − `spisanie(день)` − `ostatok(день)`.
  - Если предыдущего остатка нет (первый лист по позиции) — продано не считаем, помечаем «нет базы».
  - Отрицательное продано → флаг аномалии (ошибка распознавания/учёта) на ревью.
- **Списания/потери** = сумма `spisanie` по периоду/позиции/точке.
- **Динамика** прихода/остатка/продаж по дням.

## 9. Aging (Точка 2, десерты)

Метрика устойчива к нерегулярному заполнению листов:

> **Возраст остатка** = дней с последнего «прихода» по позиции, пока остаток > 0.
> Если возраст > порога → флаг «залежалось».

- Порог по умолчанию **5 дней**; настраивается на товар через `shelf_life_days`.
- Считается из `movements` (нужны события прихода + текущий остаток > 0) — отдельных данных не требует.
- Поверхность: блок «Залежалось > N дней» в дашборде Точки 2 + опц. алерт в Telegram (дайджест).
- Включается, как только по позициям накопятся остатки за несколько дней (данные есть → метрика живая).

## 10. Дашборд v1

- **Главный экран — Остатки** по точкам: таблица позиций с текущим остатком, фильтр по точке/типу/дате.
- **Продажи по товарам** (вычисленные) — за период, по точкам.
- **Списания / потери** — топ позиций, динамика.
- **Точка 2 → «Залежалось > N дней»** — список с возрастом остатка (когда aging включён).
- **Загрузка/ревью листов** — статусы листов, очередь `needs_review`, блок `unknown_lines`.
- **Каталог** (админка) — SKU, aliases, `shelf_life_days`, активность.

Деньги (₽) на дашборде не показываем в Фазе 1.

- Данные — операционные по пекарне (без платёжной/персональной чувствительности в Фазе 1), но доступ

## 12. Краевые случаи

- **Многодневный лист:** один снимок → movements на каждую распознанную дату-колонку.
- **Повторная загрузка того же листа:** дедуп по `image_hash` и/или `(point, type, dates)`;
  существующие movements обновляются (с сохранением `manually_edited`), не дублируются.
- **Новые/дописанные от руки строки** (нет в каталоге) → `unknown_lines` на решение человека.
- **Пустые ячейки** → null (не 0): «не заполняли» ≠ «ноль остатка».
- **Корректировки «x−y», партии «a+b»** → парсятся в одно число, но `raw_cell` сохраняется.
- **Кривое фото** (блики/угол/обрезка края, как в образцах) → предобработка + предупреждения; если не
  читается — `needs_review` без выдумывания чисел.
- **Отрицательное/несходящееся продано** → флаг аномалии, не молчим.
- **Несколько листов на одну дату/точку** (пироги + десерты) → разные `sheet_type`, не конфликтуют.

## 15. Критерии готовности Фазы 1

- Загрузка листа (Telegram и веб) → распознавание → подтверждение с правками → запись в `movements`.
- Каталог SKU по обеим точкам и трём типам листов ведётся в админке.
- Дашборд показывает **реальные остатки** по точкам, продажи и списания по товарам/дням.
- Метрика aging реализована и включается для Точки 2 (порог настраивается).
- Краевые случаи из §12 обрабатываются (особенно: ничего не выдумываем, `raw_cell` сохраняется,
  дубли не плодятся, пустое ≠ ноль).
