## 1. Контекст

Фаза 1 (веб-цикл захвата и ревью листов движения товара) готова и в проде: остатки/продажи/списания
считаются из `movements`, есть aging-метрика. Теперь нужен **дашборд**, и главное требование Nikas:

Интеграций с iiko Cloud API и Т-Бизнес API пока нет (они были отложены в Ф2/Ф3). Решение по этой фазе:
**финансы вводятся вручную и/или импортом CSV**, а реальные API подключим отдельной фазой позже.
Публичная сигнатура и операционное ядро Фазы 1 не меняются — финансы это новый, изолированный слой.

Бренд: **Nikas Cafe**, мятно-зелёный фирменный цвет + белый рукописный логотип. Две точки получают
реальные имена: **Точка 1 → Плюшкино**, **Точка 2 → Корица** (id остаются `point-1` / `point-2`).

## 2. Цели Фазы 4

1. **Дашборд `/`** — единый экран: финансы сверху, операционка (с листов) ниже. Фильтр по точке
   (Все / Плюшкино / Корица) и по периоду (месяц).
2. **Чистая прибыль** — главный KPI: выручка − расходы, по точкам и периоду, с динамикой к прошлому периоду.
3. **Финансовый слой** — ручной ввод и импорт CSV выручки (по дням, по точкам) и расходов
   (по дням, по точкам, **с категориями**).
4. **Структура расходов** — пончик по категориям.
5. **Операционные блоки** на дашборде из данных Фазы 1: остатки сейчас, aging (Корица >N дней),
   списания (топ), очередь листов на проверке.
6. **Бренд Nikas Cafe** — мятный светлый стиль (направление A), логотип, переименование точек.

### Не-цели Фазы 4 (out of scope)

- Реальные интеграции iiko Cloud / Т-Бизнес API (отдельная фаза). Здесь — ручной ввод/CSV.
- Перевод штук в деньги по прайсу (продажи на дашборде — в штуках, как в Ф1; деньги — отдельные суммы
  выручки/расходов, не по позициям).
- Сверка бумажных продаж с кассой iiko (Ф3).
- Бюджеты/планирование, налоги, P&L по стандартам учёта.
- Мультивалютность (только ₽).
- Редактор категорий расходов в UI (набор фиксирован в этой фазе, см. §5).

## 5. Модель данных (дополнения к схеме Prisma)

Точки уже есть (`Point`, id `point-1`/`point-2`) — **переименовать**: `name` → «Плюшкино» / «Корица»
(сид `prisma/seed.ts` + апдейт в БД; id и связи не трогаем).

### `Revenue` (выручка, источник — iiko; пока вручную/CSV)
- `id`, `pointId` (fk Point), `date` (`@db.Date`),
- `amount` (`Decimal @db.Decimal(12,2)`, ₽),
- `source` (`RevenueSource`: `manual` | `import`), `note` (String?),
- `createdBy` (String?), `createdAt`, `updatedAt`.
- Уникальность: `@@unique([pointId, date])` — одна строка выручки на точку/день; повторный ввод/импорт
  обновляет (upsert), не дублирует.

### `Expense` (расходы, источник — Т-Бизнес; пока вручную/CSV)
- `id`, `pointId` (fk Point), `date` (`@db.Date`),
- `amount` (`Decimal @db.Decimal(12,2)`, ₽),
- `category` (`ExpenseCategory`),
- `source` (`ExpenseSource`: `manual` | `import`), `note` (String?),
- `createdBy` (String?), `createdAt`, `updatedAt`.
- Индекс `@@index([pointId, date])`. Без уникальности: за день на точке может быть несколько расходов
  разных категорий и несколько платежей в одной категории (каждый платёж — строка).

### Enum `ExpenseCategory`
`produkty` (Продукты/сырьё) · `arenda` (Аренда) · `fot` (ФОТ/зарплата) ·
`kommunalka` (Коммуналка/услуги) · `prochee` (Прочее).
> Набор фиксирован в этой фазе. Метки (рус.) — в одном словаре на фронте/бэке.

### Enum `RevenueSource` / `ExpenseSource`: `manual` | `import`.

Денежная сумма — `Decimal(12,2)`. При выдаче в API/во фронт сериализовать в number (через `Number(d)`),
агрегаты считать на стороне БД/в рублях целыми копейками не усложняем (₽ с копейками, округление при показе).

## 6. Дашборд `/` (раскладка одобрена)

Серверный компонент (`runtime='nodejs'`, `force-dynamic`), читает агрегаты по выбранным точке+периоду.
Фильтры в query-параметрах: `?point=all|point-1|point-2&month=YYYY-MM` (по умолчанию текущий месяц, все точки).

**Блоки сверху вниз:**

1. **KPI-ряд (4 карточки):**
   - **Чистая прибыль** (крупная, зелёная `--profit`): `выручка − расходы` за период/точку; дельта к прошлому месяцу (▲/▼ %).
   - **Выручка (iiko)**: сумма `Revenue.amount`; дельта.
   - **Расходы (Т-Бизнес)**: сумма `Expense.amount`; дельта.
   - **Маржинальность**: `прибыль / выручка * 100%` (если выручка 0 → «—»); дельта в п.п.
2. **Графики (2 колонки):**
   - **Выручка и прибыль по дням** — столбики по дням месяца (две серии: выручка, прибыль). Прибыль(день) =
     выручка(день) − расходы(день).
   - **Структура расходов** — пончик по `ExpenseCategory` (% и суммы) + легенда.
3. **Операционка (2 колонки):**
   - **Остатки сейчас** — таблица из `movements` (товар · точка · текущий остаток · продано за период).
     Текущий остаток = `ostatok` последней даты с заполненным остатком (логика Ф1). Фильтр по точке применяется.
   - **Залежалось >N дней · Корица** — aging-блок (десерты Точки 2): товар · возраст остатка · остаток;
     строки с возрастом > порога (`shelfLifeDays`, по умолч. 5) подсвечены. Виден только когда фильтр = Все или Корица.
4. **Низ (2 колонки):**
   - **Списания за период (топ)** — топ позиций по сумме `spisanie` (товар · точка · списано шт).
   - **Листы на проверке** — очередь `needs_review` (дата · точка · тип · ссылка на `/sheets/[id]`).

Пустые состояния: если финансов за период нет — KPI показывают ₽0 и подсказку «Внесите выручку/расходы на
странице Финансы». Если листов нет — операционные блоки показывают «нет данных».

## 7. Страница `/finance` (ввод + импорт + журнал)

Три части на одной странице:

1. **Быстрый ввод (форма):**
   - Тип: Выручка | Расход. Дата. Точка (Плюшкино/Корица). Сумма (₽).
   - Для расхода — Категория (из enum). Заметка (опц.).
   - Сохранение → `POST /api/finance` → запись с `source='manual'`. Выручка — upsert по (точка, дата).
2. **Импорт CSV:**
   - Загрузка файла. Ожидаемый формат документирован (см. ниже). Превью распознанных строк → подтверждение → запись с `source='import'`.
   - **Формат CSV выручки:** заголовки `date,point,amount` (date `YYYY-MM-DD` или `DD.MM.YYYY`; point — `Плюшкино`/`Корица` или `point-1`/`point-2`; amount — число, запятая/точка как десятичный разделитель).
   - **Формат CSV расходов:** `date,point,category,amount[,note]` (category — рус. метка или ключ enum).
   - Парсинг: строки, не прошедшие валидацию, показываются с причиной и не импортируются (ничего не выдумываем). Сопоставление категории по словарю меток (рус.→enum), нераспознанная категория → `prochee` с пометкой в превью.
   - Реальные выгрузки Т-Бизнес/iiko имеют свои форматы — маппинг колонок под конкретные выгрузки уточним,
     когда увидим файлы; в v1 — документированный простой формат + ручной ввод как основной путь.
3. **Журнал записей** — таблица последних записей (дата · точка · тип · категория · сумма · источник) с
   удалением строки (`DELETE /api/finance/[id]`).

Чистые модули (юнит-тест): парсер/валидатор CSV (`finance-csv.ts`), валидатор полей формы/боди
(`finance-input.ts`), агрегатор дашборда (`dashboard-aggregate.ts` — суммы/дельты/структура по входным
данным). БД-функции (репозиторий выручки/расходов, агрегирующие запросы) — тонкие обёртки, проверяются
интеграционно/в preview.

## 8. Вычисления (агрегаты дашборда)

Вход: выбранные точка(и) + месяц. Период = выбранный месяц `[1-е..конец]`; «прошлый период» = предыдущий месяц.

- **Выручка(период)** = Σ `Revenue.amount` по точке(ам)/датам периода.
- **Расходы(период)** = Σ `Expense.amount`.
- **Чистая прибыль(период)** = Выручка − Расходы.
- **Маржинальность** = прибыль / выручка · 100% (выручка 0 → «—»).
- **Дельты** — то же за прошлый месяц, разница в % (или п.п. для маржи). Нет базы → дельта скрыта.
- **По дням** — выручка(день) и прибыль(день)=выручка(день)−расходы(день) для столбиков.
- **Структура расходов** — Σ по `ExpenseCategory`, % от общих расходов.
- **Операционка** — переиспользует существующее ядро Ф1: текущий остаток, продано (`soldCalc`), списания, aging.

Денежные агрегаты по `Decimal` считать в запросах (Prisma `aggregate`/`groupBy`) либо в JS после выборки;
во фронт отдавать number, показывать с разделением разрядов и «₽».

## 9. Краевые случаи

- **Нет финансов за период** → KPI = ₽0, подсказка вести на `/finance`. Маржа «—».
- **Выручка есть, расходов нет** (или наоборот) → прибыль = выручка (или −расходы); показываем как есть.
- **Дубль выручки на точку/день** → upsert (обновление), не дубль. Расходы — много строк допустимо.
- **CSV кривой/неполный** → строки с ошибкой не импортируются, показываем причину; частичный импорт допустим.
- **Фильтр = одна точка** → aging-блок Корицы скрыт, если выбрана Плюшкино.
- **Удаление записи финансов** — мягко (DELETE строки); дашборд пересчитывается (force-dynamic).
- **Отрицательная прибыль** — показываем красным, это валидно (убыточный период).
- Деньги только ₽, без копеечной арифметики проблем (Decimal(12,2)).

## 10. Последовательность реализации (ориентир для плана)

Фаза 4 объёмна — план реализации, вероятно, разобьёт её на два этапа (каждый самостоятельно ценен):

- **4a — Финансовый слой:** переименование точек; модели `Revenue`/`Expense` + enum; миграция/`db push`;
  репозиторий; чистые `finance-input` + `finance-csv` (TDD); страница `/finance` (форма + импорт + журнал) +
  `/api/finance`. Итог: можно вносить выручку/расходы.
- **4b — Дашборд:** агрегатор (TDD); серверная страница `/` со всеми блоками (KPI, графики, операционка);
  перенос списка листов на `/sheets`; обновление навигации; бренд (логотип, токены, мятный стиль);
  preview-проверка e2e. Итог: дашборд с чистой прибылью.

Графики: лёгкая библиотека (напр. `recharts`) или собственные SVG/CSS-бары (как в мокапе) — решит план;
склоняемся к минимуму зависимостей (CSS/SVG-бары + CSS-conic пончик), как в одобренном мокапе.
